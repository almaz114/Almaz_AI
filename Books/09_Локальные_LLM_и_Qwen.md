# 1. Мы дошли до настоящей LLM

В предыдущих главах путь выглядел так:

```text
Tokens
↓
Embeddings
↓
Attention
↓
Transformer Block
```

Настоящая LLM содержит много таких блоков и огромное количество обучаемых параметров.

Упрощённо:

```text
Text
↓
Tokenizer
↓
Token IDs
↓
Embeddings
↓
Transformer Block × N
↓
Logits
↓
Next Token
```

# 2. Что такое LLM

LLM — Large Language Model.

Это большая нейронная сеть, обученная работать с последовательностями токенов.

Главная базовая задача генеративной LLM:

> Предсказать следующий Token на основании предыдущего контекста.

Например:

```text
"Сегодня хорошая ..."
```

модель оценивает вероятности возможных продолжений:

```text
погода
новость
идея
возможность
...
```

---

# 3. LLM не хранит текст как базу данных

Модель не является обычной таблицей:

```text
вопрос → готовый ответ
```

Во время обучения информация распределяется по огромному количеству весов.

Поэтому правильнее думать:

```text
LLM
=
архитектура
+
обученные параметры
+
Tokenizer
+
правила генерации
```

---

# 4. Архитектура и веса — разные вещи

Архитектура описывает:

```text
какие слои есть
как они соединены
сколько Transformer Blocks
какие размерности
какой Attention
```

Weights — конкретные числа внутри этих слоёв.

Две модели могут иметь похожую архитектуру, но совершенно разные обученные веса.

---

# 5. Что означает количество параметров

Можно встретить:

```text
0.5B
1.5B
4B
7B
14B
32B
...
```

`B` означает billions — миллиарды параметров.

Например:

```text
4B
≈ 4 миллиарда параметров
```

Это не означает:

```text
4 миллиарда фактов
```

Параметры — числовые коэффициенты нейросети.

![[Images/chapter09/02_parameters_weights.png]]

# 6. Что такое inference

`Inference` — использование уже обученной модели.

Например:

```text
Prompt
↓
Model
↓
Generated Answer
```

При обычном inference веса модели не обучаются.

Это принципиально отличается от:

```text
Training
Fine-tuning
```

---

# 7. Training и Inference

Training:

```text
Dataset
↓
Forward
↓
Loss
↓
Backward
↓
Optimizer
↓
изменение weights
```

Inference:

```text
Prompt
↓
Forward
↓
Logits
↓
выбор следующего Token
```

Во время обычной генерации:

```text
backward() нет
optimizer.step() нет
```

---

# 8. Как модель генерирует текст

Пусть Prompt:

```text
"Искусственный интеллект — это"
```

Модель:

```text
1. получает Tokens
2. вычисляет Logits следующего Token
3. выбирает Token
4. добавляет его к последовательности
5. снова выполняет Forward Pass
6. повторяет цикл
```

Получаем авторегрессионную генерацию.

---

# 9. Авторегрессия

Упрощённо:

```text
Я
↓
Я люблю
↓
Я люблю машинное
↓
Я люблю машинное обучение
↓
...
```

Каждый новый Token становится частью контекста для следующего шага.

---

# 10. Tokenizer всё ещё критически важен

В главе 7 мы изучали Tokenizer.

В настоящей модели он должен соответствовать конкретной модели.

Упрощённо:

```text
Text
↓
Tokenizer модели
↓
Token IDs
↓
LLM
```

Нельзя считать Tokenizer случайной дополнительной утилитой — это часть полного pipeline модели.

---

# 11. Chat Template

Современная chat-модель обычно получает не просто строку.

Диалог может быть структурирован:

```text
system
user
assistant
```

Chat Template преобразует сообщения в последовательность специальных Tokens в формате, которому модель обучена.

---

# 12. System Prompt

System Prompt задаёт общие инструкции.

Пример:

```text
Ты технический помощник.
Отвечай кратко и по существу.
```

Далее:

```text
System
↓
User
↓
Assistant
```

формируют контекст диалога.

---

# 13. Context Window

Модель не может видеть бесконечный текст.

Есть максимальный контекст:

```text
Context Window
```

Он измеряется в Tokens.

В контекст входят:

```text
System Prompt
история диалога
текущий Prompt
документы RAG
сгенерированные Tokens
```

---

![[Images/chapter09/03_context_window.png]]

---

# 14. Почему Tokens, а не символы

Например:

```text
1000 символов
```

не означает:

```text
1000 Tokens
```

Количество Tokens зависит от Tokenizer и текста.

Поэтому ограничения контекста всегда правильнее рассматривать в Tokens.

---

# 15. KV Cache — базовая идея

При генерации каждый следующий Token использует предыдущий контекст.

Если каждый раз полностью пересчитывать всё с нуля, это дорого.

Поэтому Transformer сохраняет часть уже вычисленных:

```text
Keys
Values
```

в:

```text
KV Cache
```

Это ускоряет дальнейшую генерацию, но требует памяти.

---

# 16. Logits → следующий Token

Последний слой модели выдаёт Logits для Vocabulary.

Например:

```text
Vocabulary Size = 150000
```

Тогда для следующей позиции модель может выдать:

```text
150000 logits
```

После этого алгоритм decoding выбирает следующий Token.

---

# 17. Greedy decoding

Самый простой вариант:

```text
выбрать Token с максимальным Logit
```

То есть:

```python
next_token = argmax(logits)
```

Это детерминированный подход.

Но генерация может стать слишком однообразной.

---

# 18. Temperature

Temperature изменяет распределение вероятностей.

Упрощённо:

```text
низкая Temperature
↓
модель более предсказуема

высокая Temperature
↓
больше разнообразия и случайности
```

Например:

```text
temperature = 0.1
```

обычно делает ответы более стабильными, чем:

```text
temperature = 1.2
```

---

# 19. Top-p

Top-p — способ ограничить выбор наиболее вероятной областью распределения.

Упрощённо:

```text
берём наиболее вероятные Tokens
пока их суммарная вероятность
не достигнет p
```

Например:

```text
top_p = 0.9
```

---

![[Images/chapter09/04_sampling_temperature_top_p.png]]

---

# 20. Sampling — это не знания модели

Важно разделять:

```text
что модель знает / умеет
```

и:

```text
как мы выбираем следующий Token
```

Temperature и Top-p меняют процесс выбора, но не добавляют модели новых знаний.

---

# 21. Почему локальные модели требуют много памяти

Параметры нужно разместить в памяти.

Если каждый параметр хранить в высокой точности, потребуется много RAM/VRAM.

Поэтому локальные модели часто используют:

```text
Quantization
```

---

# 22. Что такое Quantization

Квантизация уменьшает точность хранения weights.

Упрощённо:

```text
больше бит на параметр
↓
больше памяти
обычно выше точность представления

меньше бит
↓
меньше памяти
быстрее/доступнее локальный запуск
возможна потеря качества
```

---

# 23. Q4, Q5, Q8 — базовая идея

В локальной экосистеме можно встретить обозначения:

```text
Q4
Q5
Q8
```

Упрощённо они указывают на более низкую точность хранения weights.

Это не универсальная шкала качества сама по себе: конкретные форматы квантизации могут отличаться.

Главная идея:

```text
Quantization
=
компромисс
память ↔ скорость ↔ качество
```

![[Images/chapter09/05_quantization_memory.png]]

# 24. RAM и VRAM

RAM:

```text
оперативная память компьютера
```

VRAM:

```text
память видеокарты
```

Если модель выполняется на GPU, VRAM особенно важна.

Если всё или часть модели выполняется на CPU:

```text
RAM тоже критична
```

---

# 25. GPU не всегда обязателен

Небольшую квантизированную модель можно запускать на CPU.

Но:

```text
GPU
```

обычно значительно ускоряет inference, особенно для более крупных моделей.

---

# 26. Что такое локальная модель

Локальная LLM работает на вашем компьютере или сервере.

Преимущества:

```text
данные могут оставаться локально
можно работать офлайн
контроль над моделью
возможность интеграции со своими приложениями
```

Недостатки:

```text
нужно железо
ограниченная скорость
настройка окружения
локальная модель может быть слабее крупных облачных систем
```

---

# 27. Где здесь Qwen

Qwen — семейство открытых языковых моделей.

В рамках курса Qwen удобно использовать как пример настоящей локальной Transformer-модели.

Наша цель сейчас не изучить все версии Qwen, а понять общий pipeline:

```text
Qwen
↓
Tokenizer
↓
Model Weights
↓
Local Runtime
↓
Prompt
↓
Generated Tokens
```

# 28. Ollama

Ollama — один из удобных способов запускать локальные LLM.

Упрощённая архитектура:

```text
Python application
↓
Ollama
↓
Local Qwen model
↓
Response
```

Ollama берёт на себя значительную часть инфраструктуры локального inference.

# 29. Запрос из Python

Если Ollama установлен и нужная модель уже доступна локально, идея кода выглядит так:

```python
from ollama import chat

response = chat(
    model=MODEL_NAME,
    messages=[
        {
            "role": "user",
            "content": "Объясни, что такое Token."
        }
    ],
)

print(response["message"]["content"])
```

Конкретное имя локальной модели зависит от того, какую модель вы установили.

---

# 30. Почему имя модели вынесем в настройку

Не будем жёстко привязывать учебный код к одной версии.

Например:

```python
MODEL_NAME = "your-local-qwen-model"
```

Пользователь заменяет значение на имя своей установленной модели.

Это полезнее, чем привязывать курс к быстро меняющемуся названию конкретного релиза.

# 33. Почему Prompt влияет на ответ

Weights остаются теми же.

Но меняется Context.

Например:

```text
"Что такое Python?"
```

и:

```text
"Объясни Python начинающему программисту в 3 предложениях."
```

могут давать разные ответы.

Это:

```text
Prompting
```

а не Fine-tuning.

---

# 34. Prompting ≠ Fine-tuning

Prompting:

```text
weights не меняются
```

Fine-tuning:

```text
часть параметров или адаптеров обучается
```

Эту разницу нужно чётко понимать перед будущей главой о LoRA/QLoRA.
