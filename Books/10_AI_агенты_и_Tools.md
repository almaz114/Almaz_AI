# 🛠️ Глава 10. AI-агенты и Tools

> **Главная цель главы:** понять, как языковая модель превращается из обычного генератора текста в систему, которая умеет выбирать инструменты, вызывать Python-функции, получать результаты и продолжать рассуждение на их основе.

# 1. Обычная LLM и агент — не одно и то же

Обычная языковая модель:

```text
Prompt
↓
LLM
↓
Text Response
```

Она может написать:

```text
"Чтобы узнать содержимое файла, откройте его."
```

Но сама по себе модель не обязана иметь доступ к файлу.

Агент добавляет слой действий:

```text
Prompt
↓
LLM
↓
решение использовать Tool
↓
Tool
↓
Result
↓
LLM
↓
Final Answer
```

# 2. Что такое Tool

Tool — внешняя функция или возможность, которую агент может вызвать.

Примеры:

```text
прочитать файл
найти данные в CSV
выполнить расчёт
получить курс валют
запросить API
поискать запись в базе данных
сохранить результат
```

С точки зрения Python Tool часто является обычной функцией.

Например:

```python
def add_numbers(a: float, b: float) -> float:
    return a + b
```

---

# 3. Модель не выполняет Python сама

Очень важное разделение:

```text
LLM
↓
решает, какой Tool нужен
```

а:

```text
Python runtime
↓
реально выполняет функцию
```

То есть модель может сформировать намерение:

```text
tool = "add_numbers"
arguments = {"a": 10, "b": 20}
```

Но вычисление выполняет уже код приложения.

---

# 4. Tool Calling

Tool Calling — механизм, при котором модель возвращает структурированное описание вызова инструмента.

Упрощённый пример:

```json
{
  "tool_name": "add_numbers",
  "arguments": {
    "a": 10,
    "b": 20
  }
}
```

Приложение читает эту структуру и вызывает нужную Python-функцию.

# 5. Agent Loop

Главный цикл агента:

```text
User
↓
Model
↓
нужен Tool?
├── нет → Final Answer
└── да
    ↓
    Tool Call
    ↓
    Tool Execution
    ↓
    Observation
    ↓
    Model
    ↓
    следующий шаг
```

Этот цикл может выполняться несколько раз.

---

# 6. Observation

Observation — результат инструмента, который возвращается модели.

Например:

```text
Tool:
read_file("report.txt")

Observation:
"Выручка за месяц составила 1 240 000 рублей."
```

Теперь модель может использовать этот результат при формировании ответа.

---

# 7. Tool Schema

Модели нужно объяснить:

```text
как называется Tool
что он делает
какие аргументы принимает
каких типов эти аргументы
```

Упрощённо:

```json
{
  "name": "add_numbers",
  "description": "Складывает два числа",
  "parameters": {
    "a": "number",
    "b": "number"
  }
}
```

Это Tool Schema.

# 8. Почему описание Tool важно

Если написать только:

```text
name = "calculate"
```

модели непонятно:

```text
что именно считать?
какие параметры нужны?
какой формат результата?
```

Хорошее описание должно быть конкретным.

Например:

```text
"Возвращает сумму двух чисел a и b."
```

лучше, чем:

```text
"Выполняет вычисления."
```

---

# 9. Tool Registry

Если инструментов несколько, удобно хранить их в реестре.

Например:

```python
TOOLS = {
    "add_numbers": add_numbers,
    "word_count": word_count,
    "get_note": get_note,
}
```

Теперь по имени можно найти реальную функцию.

# 10. Dispatcher

Dispatcher — код, который получает:

```text
tool_name
arguments
```

и выполняет нужную функцию.

Пример:

```python
def execute_tool(tool_name, arguments):
    tool = TOOLS[tool_name]
    return tool(**arguments)
```

В реальном приложении нужно добавить проверки и обработку ошибок.

---

# 11. Аргументы нельзя принимать вслепую

Модель может ошибиться и вернуть:

```text
неправильное имя аргумента
неправильный тип
пропущенное обязательное поле
лишнее поле
```

Поэтому приложение должно валидировать Tool Call.

---

# 12. Ошибки Tool

Инструмент может завершиться ошибкой.

Например:

```text
файл не найден
API недоступен
неверный путь
деление на ноль
нет прав доступа
```

Агент не должен падать полностью из-за каждой ошибки.

Лучше вернуть структурированный результат:

```json
{
  "status": "error",
  "message": "Файл не найден"
}
```

---

![[Images/chapter10/05_tool_error_safety.png]]

# 13. Tool Result должен быть понятным модели

Хороший Tool Result:

```json
{
  "status": "ok",
  "result": 42
}
```

или:

```json
{
  "status": "error",
  "message": "Не найден файл data.csv"
}
```

Структурированный результат легче использовать в Agent Loop.

---

# 14. Агент и обычный Python-код

Агент не заменяет Python.

Наоборот:

```text
Python
↓
реализует надёжные операции
```

а:

```text
LLM
↓
выбирает подходящий инструмент
и интерпретирует результат
```

Это сильное разделение обязанностей.

---

# 15. Что лучше делать Tool-ом

Tool хорошо подходит для операций, где нужен точный результат.

Например:

```text
математика
работа с файлами
SQL
API
поиск данных
получение текущего состояния системы
```

Не стоит заставлять LLM «угадывать» то, что может точно вычислить код.

---

# 16. Пример: подсчёт слов

Tool:

```python
def word_count(text: str) -> int:
    return len(text.split())
```

Пользователь:

```text
Сколько слов в этом тексте?
```

Агент может выбрать `word_count`.

---

# 17. Пример: чтение заметки

Tool:

```python
def get_note(name: str) -> str:
    ...
```

Пользователь:

```text
Что написано в заметке chapter10?
```

Модель не должна придумывать содержимое.

Она должна вызвать Tool.

---

# 18. Несколько инструментов

Представим:

```text
add_numbers
word_count
get_note
```

Пользователь спрашивает:

```text
Сколько слов в моей заметке?
```

Агент потенциально должен выполнить два шага:

```text
1. get_note
2. word_count
```

Это уже настоящий многошаговый Agent Loop.

---

# 19. Planner и Executor — базовая идея

Иногда архитектуру удобно мысленно разделять:

```text
Planner
↓
решает, что делать

Executor
↓
выполняет Tool
```

В маленьком агенте обе роли могут находиться в одном цикле.

---

# 20. Когда агент должен остановиться

Agent Loop не должен быть бесконечным.

Нужно ограничивать:

```text
max_steps
```

Например:

```python
MAX_STEPS = 5
```

Если модель не смогла завершить задачу за 5 шагов, приложение останавливает цикл.

---

# 21. Почему нужны ограничения

Без ограничений агент может:

```text
повторять один Tool
зациклиться
вызывать дорогие API
создавать слишком много файлов
выполнять лишние действия
```

Поэтому orchestration-код обязан контролировать процесс.

---

# 22. Read-only и write Tools

Полезно различать:

```text
Read-only Tool
```

например:

```text
прочитать файл
найти данные
посчитать
```

и:

```text
Write Tool
```

например:

```text
удалить файл
изменить БД
отправить сообщение
создать ордер
```

Write Tools требуют особенно строгого контроля.

---

# 23. Принцип минимальных разрешений

Агенту нужно давать только те возможности, которые действительно нужны.

Например, если задача:

```text
анализ CSV
```

не нужно давать Tool:

```text
delete_any_file
```

---

# 24. Human-in-the-loop

Для важных действий полезна схема:

```text
Model предлагает действие
↓
Пользователь подтверждает
↓
Tool выполняется
```

Это особенно важно для:

```text
финансовых операций
удаления данных
отправки сообщений
изменения внешних систем
```

---

# 25. Локальная LLM + Tools

Теперь соединяем главу 9 и главу 10:

```text
Local Qwen
↓
Tool Call
↓
Python Tool
↓
Observation
↓
Local Qwen
↓
Answer
```

То есть сама модель может оставаться локальной, а инструменты — быть вашими Python-функциями.

---

# 26. Tool Registry как расширяемая архитектура

Сегодня:

```text
3 Tools
```

завтра:

```text
20 Tools
```

Поэтому Registry позволяет добавлять инструменты независимо от основной логики агента.

---

# 27. Собственные навыки агента

В будущем ваши Tools могут быть специализированными:

```text
read_excel
compare_files
query_database
analyze_forex_data
get_pending_orders
check_dbf_arithmetic
```

Тогда локальная модель получает доступ не к «магии», а к конкретным проверенным функциям.

---

# 28. Tool ≠ Skill ≠ Agent

Упрощённо:

```text
Tool
→ одна внешняя операция

Skill
→ более крупная логика / инструкция / набор действий

Agent
→ система, которая решает, когда и как их использовать
```

Термины в разных фреймворках могут немного отличаться, но это полезная базовая модель.

---

```text
↓

```
