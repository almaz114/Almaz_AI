# 1. Главная цель

Моя цель — не создавать искусственный интеллект полностью с нуля, а научиться использовать уже готовые открытые модели и строить на их основе собственные интеллектуальные системы.

В перспективе такая система должна уметь:

- работать на базе открытой языковой модели, например семейства Qwen;
- использовать мои собственные инструкции и правила;
- обращаться к документации и рабочим файлам;
- вызывать мои Python-функции и инструменты;
- работать с Excel, DBF, API, базами данных и MetaTrader 5;
- сохранять состояние и историю выполнения;
- визуально показывать, какие действия выполняет агент;
- при необходимости быть дообученной под конкретное поведение.

Мой путь должен строиться не вокруг сухой математики, а вокруг **наглядных схем, небольших экспериментов и реальных Python-проектов**.

# 3. Из каких частей состоит будущая AI-система

Нужно сразу разделять несколько разных компонентов.

## 3.1. Языковая модель

Языковая модель — это нейросеть, которая получает последовательность токенов и предсказывает, какой токен должен идти следующим.

Примеры:

- Qwen;
- Llama;
- Mistral;
- Gemma;
- другие открытые модели.

Модель сама по себе не является полноценным агентом. Она только обрабатывает входной контекст и генерирует продолжение.

## 3.2. Системные инструкции

Системные инструкции определяют общие правила поведения:

- роль модели;
- допустимые действия;
- формат результата;
- порядок принятия решений;
- ограничения безопасности;
- условия вызова инструментов.

## 3.3. RAG

RAG предоставляет модели внешние знания во время выполнения запроса.

Через RAG можно передавать:

- документацию проекта;
- технические задания;
- инструкции;
- содержимое файлов;
- актуальные сведения;
- найденные фрагменты базы знаний.

При этом параметры модели не изменяются.

## 3.4. Skills

Skill — это отдельное описание того, как выполнять определённую задачу.

Например:

- как анализировать Excel;
- как проверять DBF;
- как читать структуру проекта;
- как работать с MetaTrader 5;
- как формировать отчёт;
- как обрабатывать ошибки.

Skill можно представить как подробную инструкцию или регламент для конкретного типа работы.

## 3.5. Tools

Tools — реальные функции и программы, которые агент может вызвать.

Примеры моих будущих инструментов:

- `inspect_table_file`;
- `read_excel_filtered`;
- `export_excel_filtered`;
- `check_dbf_arithmetic`;
- получение данных из MetaTrader 5;
- чтение файлов проекта;
- обращение к Django API;
- запись результата в JSON, Excel или базу данных.

## 3.6. Память и состояние

Память хранит информацию, которая нужна между шагами или диалогами:

- историю сообщений;
- выбранный проект;
- результаты предыдущих инструментов;
- статусы выполнения;
- пользовательские настройки;
- данные текущего рабочего процесса.

## 3.7. Наблюдаемость

Наблюдаемость позволяет увидеть:

- какой промпт получила модель;
- какой инструмент она выбрала;
- какие аргументы передала;
- какой результат вернул инструмент;
- сколько заняло выполнение;
- где возникла ошибка;
- как сформировался итоговый ответ.

# 4. Как языковая модель получает и обрабатывает информацию

Рассмотрим запрос:

```text
Проверь файл Excel
```

Внутри модели происходит упрощённо следующая последовательность:

```text
Исходный текст
        ↓
Токенизация
        ↓
Токены и их числовые идентификаторы
        ↓
Векторные представления — embeddings
        ↓
Слои Transformer
        │
        ├── Self-Attention
        ├── Query, Key, Value
        ├── Multi-Head Attention
        ├── Нормализация
        ├── MLP-слои
        └── Остаточные связи
        ↓
Logits — оценки следующего токена
        ↓
Преобразование в вероятности
        ↓
Выбор следующего токена
        ↓
Добавление токена в последовательность
        ↓
Повторение цикла
        ↓
Готовый ответ
```

## 4.1. Токенизация

Модель не получает текст непосредственно в виде слов. Сначала токенизатор разбивает его на небольшие элементы — токены.

Один токен может быть:

- целым словом;
- частью слова;
- знаком пунктуации;
- числом;
- фрагментом программного кода;
- специальным служебным символом.

Затем каждому токену назначается числовой идентификатор.

## 4.2. Embeddings

Числовой идентификатор токена преобразуется в вектор — набор чисел.

Этот вектор не является обычным определением слова. Он представляет положение токена в многомерном пространстве признаков.

## 4.3. Attention

Механизм внимания помогает модели определить, какие части контекста важны для текущего токена.

Например, в длинном запросе модель может связать:

- название файла с операцией чтения;
- параметр фильтра с нужной колонкой;
- местоимение с ранее упомянутым объектом;
- имя Python-функции с описанием инструмента.

## 4.4. Предсказание следующего токена

На выходе модель получает оценки для всех токенов своего словаря.

После этого алгоритм генерации выбирает следующий токен с учётом:

- вероятностей;
- температуры;
- ограничений выборки;
- уже сгенерированного текста;
- системных инструкций;
- контекста диалога.

Затем процесс повторяется до завершения ответа.

> Модель не достаёт готовый ответ из внутренней таблицы. Она пошагово строит продолжение на основе закономерностей, записанных в её параметрах.

# 5. Как обучается нейросеть

Упрощённый цикл обучения:

```text
Обучающий пример
        ↓
Токенизация
        ↓
Модель делает предсказание
        ↓
Предсказание сравнивается с правильным продолжением
        ↓
Вычисляется loss — величина ошибки
        ↓
Backpropagation
        ↓
Вычисляются градиенты
        ↓
Optimizer изменяет обучаемые параметры
        ↓
Следующий пример
```

Этот процесс повторяется много раз.

## 5.1. Loss

`Loss` показывает, насколько предсказание модели отличается от правильного результата.

Меньшее значение loss обычно означает, что модель лучше подстраивается под обучающие данные. Но низкий training loss сам по себе не гарантирует хорошее качество на новых запросах.

## 5.2. Backpropagation

Обратное распространение ошибки определяет, как каждый обучаемый параметр повлиял на результат.

На основании этого рассчитываются градиенты.

## 5.3. Optimizer

Оптимизатор изменяет параметры модели в направлении уменьшения ошибки.

Один из важнейших параметров — `learning rate`, то есть величина шага обновления.

## 5.4. Epoch

Epoch — один полный проход по обучающей выборке.

Слишком мало эпох может привести к недообучению, а слишком много — к переобучению.

## 5.5. Batch

Batch — небольшая группа примеров, которая обрабатывается перед обновлением параметров.

При ограниченной памяти GPU используется маленький batch и `gradient accumulation`.

# 6. Виды обучения и дообучения

| Метод | Что происходит | Основная задача |
|---|---|---|
| **Pretraining** | Модель обучается на огромном массиве текстов и кода | Создание фундаментальной модели с нуля |
| **Continued pretraining** | Готовая базовая модель продолжает обучение на отраслевых текстах | Освоение специфического языка и терминологии |
| **SFT** | Модель обучается на примерах «инструкция → хороший ответ» | Формирование требуемого поведения |
| **LoRA** | Обучаются небольшие дополнительные матрицы | Экономное дообучение |
| **QLoRA** | Основная модель загружается в квантованном виде, а обучаются LoRA-адаптеры | Fine-tuning на ограниченной GPU-памяти |
| **DPO** | Используются пары предпочтительного и нежелательного ответа | Улучшение предпочтений и стиля поведения |
| **RAG** | Внешняя информация добавляется в контекст без изменения весов | Работа с документами и актуальными знаниями |

## Рекомендация для первого эксперимента

Для начала подходит:

```text
SFT
+
QLoRA
+
небольшой качественный датасет
+
готовая instruction-модель
```

Полное обучение всех параметров модели на первом этапе не требуется.

# 7. Fine-tuning, RAG, промпты, Skills и инструменты

Это центральное различие, которое необходимо хорошо понимать.

## 7.1. Когда использовать fine-tuning

Fine-tuning полезен, когда требуется устойчиво изменить поведение модели:

- отвечать в определённом формате;
- возвращать валидный JSON;
- классифицировать запросы;
- выбирать правильный инструмент;
- правильно заполнять аргументы;
- соблюдать специальный стиль;
- выполнять узкую повторяющуюся задачу;
- понимать характерные формулировки предметной области.

## 7.2. Когда использовать RAG

RAG нужен, когда требуется предоставить модели знания:

- содержание документации;
- технические задания;
- актуальные рабочие инструкции;
- данные из базы;
- сведения из файлов;
- текущие котировки;
- недавно обновлённую информацию.

RAG лучше fine-tuning для информации, которая:

- часто изменяется;
- должна иметь источник;
- хранится в документах;
- слишком объёмна;
- не обязана становиться частью поведения модели.

## 7.3. Когда использовать системный промпт

Системный промпт задаёт общие правила:

- кто такой агент;
- какую задачу он решает;
- что ему запрещено;
- как форматировать ответ;
- какие действия требуют подтверждения;
- как обрабатывать ошибку.

## 7.4. Когда использовать Skill

Skill описывает последовательность выполнения конкретной работы.

Например:

```text
Skill: проверка DBF-файла

1. Проверить существование файла.
2. Определить кодировку.
3. Проверить обязательные поля.
4. Прочитать записи.
5. Рассчитать отклонения.
6. Вернуть только проблемные строки.
7. Не изменять исходный файл.
```

## 7.5. Когда использовать Tool

Tool нужен, когда требуется реальное действие:

- открыть файл;
- выполнить расчёт;
- получить котировку;
- отправить API-запрос;
- прочитать базу данных;
- создать новый Excel-файл;
- записать результат;
- получить состояние торгового терминала.

## Главное правило выбора

```text
Нужно изменить поведение модели?
        → Fine-tuning

Нужно передать внешние знания?
        → RAG

Нужно задать правила?
        → System prompt / Skill

Нужно выполнить реальное действие?
        → Tool

Нужно сохранить состояние?
        → Memory / база данных
```

> Не следует пытаться загружать всю документацию проекта непосредственно в веса модели. Документы лучше подключать через RAG, операции выполнять инструментами, а fine-tuning использовать для устойчивого поведения.

# 8. Выбор первой модели

В качестве учебной основы можно использовать небольшую открытую модель семейства Qwen.

## Предлагаемая последовательность

### Эксперимент №1 — минимальный

```text
Модель: небольшая Qwen около 0.8B
Датасет: 50–100 примеров
Цель: пройти весь pipeline от загрузки модели до сохранения адаптера
```

### Эксперимент №2 — основной учебный

```text
Модель: Qwen около 4B
Датасет: 200–500 качественных примеров
Цель: получить заметное изменение поведения
```

### Эксперимент №3 — полноценная система

```text
Модель: Qwen около 4B
Дополнительно: RAG + Skills + Python-инструменты
Цель: создать специализированного агента
```

## Instruction-модель или Base-модель

Для первого SFT лучше использовать готовую instruction-модель.

Она уже умеет:

- вести диалог;
- следовать инструкциям;
- использовать chat template;
- формировать ответы в привычном формате.

Base-модель лучше оставить на более поздний этап, когда будут понятны:

- chat templates;
- continued pretraining;
- instruction tuning;
- форматы датасетов;
- особенности генерации.

## Важное замечание о длине контекста

Даже если модель поддерживает очень большое контекстное окно, это не означает, что первый fine-tuning нужно проводить на максимальной длине.

Для начального опыта разумно ограничить длину последовательности:

```text
512 токенов
или
1024 токена
```

Чем больше длина последовательности, тем выше расход памяти и время обучения.

## Пример стартовой конфигурации QLoRA

```text
Метод:                    QLoRA
Квантизация основной модели: 4-bit
Длина последовательности: 512 или 1024
Batch size:               1
Gradient accumulation:    4–16
Epochs:                   1–3
LoRA rank:                8 или 16
Validation dataset:       обязательно
```

Это не универсально идеальные параметры, а безопасная стартовая точка для учебного эксперимента.

# 11. Как подготовить первый датасет

Для первого проекта не нужно обучать модель торговым прогнозам или пытаться передать ей все знания предметной области.

Лучший стартовый проект — научить модель **правильно выбирать один из нескольких Python-инструментов**.

## 11.1. Пример задачи

Доступны инструменты:

```text
inspect_table_file
read_excel_filtered
check_dbf_arithmetic
```

Примеры поведения:

```text
Пользователь:
«Покажи структуру Excel-файла»

Правильное действие:
вызвать inspect_table_file
```

```text
Пользователь:
«Найди строки, где количество меньше нуля»

Правильное действие:
вызвать read_excel_filtered
```

```text
Пользователь:
«Проверь арифметические остатки в DBF»

Правильное действие:
вызвать check_dbf_arithmetic
```

```text
Пользователь:
«Объясни, что делает функция read_excel_filtered»

Правильное действие:
не вызывать инструмент, а дать текстовое объяснение
```

## 11.2. Концептуальный формат chat-датасета

```json
{
  "messages": [
    {
      "role": "system",
      "content": "Ты агент для работы с файлами через Python-инструменты."
    },
    {
      "role": "user",
      "content": "Покажи листы и колонки файла report.xlsx"
    },
    {
      "role": "assistant",
      "content": "Использую инструмент inspect_table_file для анализа структуры файла."
    }
  ]
}
```

При обучении настоящему tool calling формат должен соответствовать тому, как выбранная модель и runtime описывают вызов инструмента.

## 11.3. Количество примеров

| Количество | Цель |
|---:|---|
| 50–100 | Проверить, что весь pipeline работает |
| 200–500 | Получить заметное изменение поведения |
| 1 000–3 000 | Повысить устойчивость узкого навыка |
| 5 000+ | Улучшить разнообразие и обобщение при высоком качестве данных |

Это ориентиры, а не гарантия.

> Сто качественных, разнообразных и правильно проверенных примеров часто полезнее тысячи почти одинаковых автоматически созданных записей.

## 11.4. Какими должны быть примеры

Датасет должен включать:

- простые формулировки;
- длинные формулировки;
- разные названия файлов;
- разные порядки слов;
- разговорный язык;
- опечатки;
- лишнюю информацию;
- запросы, где инструмент нужен;
- запросы, где инструмент не нужен;
- запросы с недостаточными параметрами;
- неправильные или опасные запросы;
- примеры обработки ошибок.

## 11.5. Деление датасета

```text
80% — train
10% — validation
10% — test
```

### Train

Используется для изменения обучаемых параметров.

### Validation

Используется во время эксперимента для оценки качества и выявления переобучения.

### Test

Используется только для финального независимого сравнения.

Тестовые примеры нельзя включать в train и нежелательно многократно использовать при ручной настройке модели.

## 11.6. Контроль утечек

Нужно проверять, чтобы одинаковые или почти одинаковые запросы не оказались одновременно в train и test.

Иначе результат будет выглядеть лучше, чем реальная способность модели работать с новыми формулировками.

# 12. Как оценивать результат

Нельзя считать fine-tuning успешным только потому, что training loss уменьшается.

Нужно сравнивать:

```text
Исходная модель
        против
Модели после fine-tuning
```

на одном и том же независимом наборе запросов.

## 12.1. Что проверять

1. Правильно ли выбран инструмент.
2. Корректно ли заполнены аргументы.
3. Вызывается ли инструмент только при необходимости.
4. Соблюдается ли требуемый формат.
5. Возвращается ли валидный JSON.
6. Корректно ли модель реагирует на недостаток данных.
7. Работает ли на новых формулировках.
8. Не ухудшились ли обычные текстовые ответы.
9. Не появилась ли склонность вызывать один и тот же инструмент всегда.
10. Правильно ли обрабатываются ошибки инструмента.

## 12.2. Пример таблицы оценки

| Метрика | Исходная модель | После fine-tuning |
|---|---:|---:|
| Правильный выбор инструмента | 62% | 88% |
| Правильные аргументы | 48% | 81% |
| Лишние вызовы | 25% | 7% |
| Валидный JSON | 71% | 96% |

Цифры в таблице являются примером структуры оценки, а не ожидаемым гарантированным результатом.

## 12.3. Категории тестов

Полезно разделить тесты на группы:

- прямой запрос к инструменту;
- косвенный запрос;
- запрос без необходимости инструмента;
- запрос с отсутствующим параметром;
- запрос с неверным файлом;
- несколько возможных инструментов;
- провокация на лишний вызов;
- ошибка инструмента;
- повторный вызов после ошибки;
- обычный вопрос вне специализации.

# 16. Первый практический проект

## Название

**Учебный AI-агент для выбора Python-инструментов работы с файлами**

## Цель

Научить модель выбирать один из трёх инструментов и правильно формировать аргументы.

## Инструменты

```text
1. inspect_table_file
2. read_excel_filtered
3. check_dbf_arithmetic
```

## Шаг 1. Реализовать инструменты

Каждый инструмент должен иметь:

- понятное имя;
- подробный docstring;
- типизированные аргументы;
- предсказуемый JSON-ответ;
- обработку ошибок;
- отсутствие скрытых побочных действий.

## Шаг 2. Сделать обычного агента без fine-tuning

Сначала проверить, как исходная модель работает только на основании:

- системного промпта;
- описаний инструментов;
- нескольких примеров в prompt.

Это будет baseline.

## Шаг 3. Создать тестовый набор

Подготовить, например, 100 независимых запросов:

- 25 для просмотра структуры файла;
- 25 для фильтрации Excel;
- 25 для проверки DBF;
- 25 запросов, где инструмент не требуется или данных недостаточно.

## Шаг 4. Измерить исходное качество

Сохранить:

- правильность выбора инструмента;
- правильность аргументов;
- лишние вызовы;

## Шаг 5. Подготовить обучающий датасет

Добавить разнообразие:

- разные формулировки;
- разные имена файлов;
- короткие и длинные запросы;
- естественные опечатки;
- неполные запросы;
- отрицательные примеры.

## Шаг 6. Выполнить QLoRA

Использовать:

```text

```

## Шаг 7. Провести повторную оценку

## Шаг 8. Подключить визуализацию

```text

```

1. Улучшился ли выбор инструмента?
2. Стали ли аргументы точнее?
3. Уменьшились ли лишние вызовы?
4. Не ухудшились ли обычные ответы?
5. Оправдан ли fine-tuning или достаточно prompt engineering?

# 18. Что не нужно делать в начале

## 18.1. Не обучать модель с нуля

Pretraining требует огромных объёмов:

- данных;
- GPU;
- времени;
- инженерной инфраструктуры.

Это не соответствует учебной цели.

## 18.2. Не начинать с большой модели

Большая модель усложняет:

- настройку;
- стоимость;
- время обучения;
- поиск ошибок;
- интерпретацию результата.

## 18.3. Не загружать всю документацию в fine-tuning

Документация меняется и лучше подходит для RAG.

## 18.4. Не оценивать результат только по loss

Нужны реальные тестовые запросы и сравнение с baseline.

## 18.5. Не смешивать train и test

Иначе метрики будут недостоверными.

## 18.6. Не начинать с торговых решений

Первый эксперимент должен быть безопасным, понятным и легко проверяемым.

Выбор инструмента для Excel или DBF гораздо удобнее для обучения, чем прогноз финансового рынка.

## 18.7. Не создавать сложного автономного агента сразу

Сначала:

```text
одна модель
+
три инструмента
+
ограниченное число шагов
+
понятные тесты
```

# 21. Словарь основных терминов

| Термин | Простое объяснение |
|---|---|
| **AI / ИИ** | Общее название систем, выполняющих задачи, связанные с распознаванием, прогнозированием, генерацией и принятием решений |
| **ML** | Машинное обучение — методы, в которых поведение системы определяется данными |
| **Neural Network** | Система математических слоёв с обучаемыми параметрами |
| **Parameter / Weight** | Число внутри модели, изменяемое во время обучения |
| **Tensor** | Многомерный массив чисел |
| **Token** | Элемент текста, с которым работает модель |
| **Tokenizer** | Программа, превращающая текст в токены и обратно |
| **Embedding** | Векторное представление токена, текста или объекта |
| **Transformer** | Основная архитектура современных языковых моделей |
| **Attention** | Механизм определения связей между частями входной последовательности |
| **Query, Key, Value** | Три представления, используемые внутри attention |
| **Logits** | Числовые оценки возможных следующих токенов |
| **Softmax** | Преобразование оценок в распределение вероятностей |
| **Temperature** | Параметр случайности генерации |
| **Loss** | Численная мера ошибки модели |
| **Gradient** | Направление изменения параметров для уменьшения ошибки |
| **Optimizer** | Алгоритм обновления параметров |
| **Learning rate** | Размер шага обновления параметров |
| **Epoch** | Полный проход по обучающему набору |
| **Batch** | Группа примеров, обрабатываемых вместе |
| **Fine-tuning** | Дополнительное обучение готовой модели |
| **SFT** | Обучение на правильных примерах инструкций и ответов |
| **LoRA** | Экономное обучение небольших дополнительных матриц |
| **QLoRA** | LoRA поверх квантованной основной модели |
| **Adapter** | Небольшой набор обученных параметров, подключаемый к основной модели |
| **Quantization** | Снижение точности хранения параметров для экономии памяти |
| **RAG** | Поиск внешних данных и добавление их в контекст модели |
| **Chunk** | Небольшой фрагмент документа для индексации и поиска |
| **Vector database** | Хранилище векторов для семантического поиска |
| **Agent** | Система, где модель выбирает и выполняет действия по шагам |
| **Tool calling** | Формирование моделью структурированного вызова функции |
| **Skill** | Инструкция по выполнению конкретного типа задачи |
| **Memory** | Сохранённое состояние или история |
| **Trace** | Полная цепочка выполнения одного запроса |
| **Evaluation** | Систематическая проверка качества модели или агента |
| **Baseline** | Исходный результат, с которым сравниваются изменения |
| **Overfitting** | Переобучение на train-данных с ухудшением работы на новых примерах |

## Главный вывод

Конечная цель — не просто получить «свою дообученную модель», а построить управляемую систему, в которой каждый компонент решает свою задачу:

- **модель** понимает язык и формирует решения;
- **fine-tuning** закрепляет нужное поведение;
- **RAG** предоставляет внешние знания;
- **Skills** описывают порядок выполнения работ;
- **Tools** выполняют реальные действия;

- **LangGraph** управляет последовательностью;
- **Langfuse и TensorBoard** делают работу системы наглядной и измеримой.

Первый проект должен быть небольшим, безопасным и проверяемым: **научить открытую модель выбирать один из трёх Python-инструментов для работы с файлами, сравнить её до и после QLoRA и визуально проследить весь путь выполнения**.
